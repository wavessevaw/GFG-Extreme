# GFG Extreme — UI Audit
## 2026-10-07

Target reviewed: current `main` UI, with the product direction that GFG Extreme is an intelligent Governor around MAKO Render v4.

## Executive verdict

The visual language is good.

Keep:
- near-black / graphite surfaces;
- restrained red accent;
- large central hero;
- circular FPS target/output indicator;
- Real -> GFG -> Output flow;
- strong RUN/STOP control;
- compact typography;
- minimal rounded cards;
- current overall visual density and proportions.

The problem is not visual design.

The problem is **information architecture**.

The current UI still exposes too much legacy machinery from the previous project:
- backend choice;
- saved multiplier;
- scaling provisioning;
- profile management;
- generic All Settings editor;
- configuration journal;
- explicit launch command;
- manual log recording;
- engine reinstall/uninstall;
- Flatpak runtime version management;
- per-app Flatpak overrides;
- pipeline inspector internals.

These are useful for development, compatibility and recovery.

They are not the product.

The normal user-facing UI should communicate:

> What is GFG doing?
> Is the game healthy?
> How much power is it using/saving?
> Why did it choose this state?
> Can I switch the optimization philosophy?

Everything else should be progressively hidden.

---

# 1. Main screen: visually strong, structurally overloaded

Current Home contains:

1. device chip;
2. hero;
3. FPS ring;
4. status;
5. Real -> GFG -> Output;
6. Effort;
7. TDP bar;
8. RUN/STOP;
9. hint;
10. Governor row;
11. Frame Generation row;
12. Scaling row;
13. In-game overlay row;
14. Profile row;
15. Advanced row;
16. Launch Option section;
17. Log Recorder section.

That is too much.

The first half feels like a finished product.

The second half feels like a developer control panel bolted under it.

## Recommendation

Normal Home should contain only:

### Hero
- current state;
- target/output FPS;
- Real -> ×N -> Output;
- TDP;
- frametime;
- temperature;
- battery estimate when relevant.

### Mode
One segmented control:
- Quality
- Balanced
- Battery

### Main action
- RUN / STOP

### One details entry
- “Details” or “Governor”
- opens explanation, savings, confidence, live metrics.

### One Settings entry
Small gear, not six subsystem rows.

Everything else should disappear from Home.

---

# 2. Launch Option must not live permanently on Home

Current UI shows the launch command all the time.

That is setup information, not runtime information.

It should appear only when:
- wrapper is missing;
- current game was not launched through GFG;
- setup is incomplete.

Then show a contextual card:

> GFG is not attached to this game.
> Add the launch option once.

With:
- Copy button;
- concise instruction.

Once configured, hide it.

Do not make users stare at:
`/home/deck/.local/bin/gfg %command%`
for the rest of the product's life.

---

# 3. Log Recorder should be contextual, not permanent

“Something wrong? Send me a log” on Home is useful during beta development.

It also makes the product look unfinished.

Move Log Recorder to:

`Settings -> Diagnostics`

and surface it automatically on errors:

> GFG could not verify telemetry.
> [Record diagnostic session]

This preserves support capability without making every healthy user participate in QA.

---

# 4. Frame Generation page is mostly legacy UI

Current page exposes:
- GFG Engine;
- OptiScaler;
- In-game;
- Off;
- saved multiplier ×2 / ×3.

This conflicts with the product concept.

If GFG Extreme's core is Governor + MAKO Render v4, the normal user should not need to select the engine every session.

## Recommendation

Normal mode:
- GFG Engine is implicit/default.
- Do not expose saved multiplier.

Advanced / Compatibility:
- Frame generation source:
  - GFG Engine
  - Game Native
  - OptiScaler
  - Off

Manual multiplier belongs under:
`Developer / Manual override`

not in normal UI.

The Governor should choose the multiplier.

---

# 5. Scaling page should disappear from normal navigation

Current UI has a dedicated “Scaling” page containing one toggle:

> Scale-ready launch

This is implementation plumbing.

A smart Governor should provision the required runtime automatically when possible.

The user should not need to understand:
- Scaling Engine;
- scale-ready launch;
- relaunch requirements.

## Recommendation

Delete Scaling from normal navigation.

If provisioning is impossible automatically, expose it only when needed:

> GFG needs scaling support for deeper power optimization.
> Enable on next launch?

Then one contextual action.

Render scale itself should be shown as telemetry:
`Scale 90%`

not as a subsystem the user manages.

---

# 6. Governor page should become “Details”, not a rule book

Current Governor page exposes:
- mode;
- TDP target;
- budget tier;
- point;
- phase;
- state;
- device;
- target;
- active point;
- testing point;
- attempts;
- multiplier rules;
- saved-profile rules;
- scale rules.

This is excellent developer information.

For normal users it is too implementation-oriented.

## Recommended Details page

### Now
- State: Optimizing / Locked / Protecting
- Real FPS
- Output FPS
- Frametime
- Multiplier
- Scale
- TDP
- Temperature
- Battery estimate

### Why
Example:
> GFG chose ×3 because it saves ~4 W while real FPS and frametime remain inside your Balanced limits.

### Savings
- current estimated draw;
- estimated saving vs baseline;
- battery time gained;
- temperature reduction if measurable.

### Confidence
- Verified
- Learning
- Limited telemetry

### Optional expandable
“Technical details”

Only inside that expansion:
- active point key;
- attempts;
- ladder;
- renderer state;
- telemetry revision;
- ownership state.

---

# 7. Mode selector belongs on Home

Battery / Quality is one of the few things the user genuinely should control.

With the new philosophy there should be:

- Quality
- Balanced
- Battery

This should sit directly below the hero or directly above RUN.

Do not hide the primary user intent inside Governor -> Mode.

The Governor owns technical choices.

The user owns desired behavior.

That distinction should drive the whole UI.

---

# 8. Profiles are too prominent for an intelligent product

Current Home has a Profile row and a full CRUD screen:
- activate;
- duplicate;
- rename;
- delete;
- create.

This is inherited power-user UX.

If GFG gains a persistent GameModel, most users should not manage profiles manually at all.

## Recommendation

Normal behavior:
- game detected automatically;
- per-game learning attached automatically;
- current game name shown subtly in hero/details.

Manual profiles:
`Settings -> Advanced -> Profiles`

Potentially rename the concept later:
- Game overrides
- Per-game preferences

because “Profile” is abstract and sounds like old configuration software.

---

# 9. HUD belongs in Settings, not Home

Overlay is a legitimate user preference.

It just does not deserve a permanent Home navigation row.

Move to:

`Settings -> Overlay`

Keep:
- On/Off;
- Minimal / Standard / Detailed;
- position.

Future improvement:
instead of four corner buttons, show a small visual 2×2 placement picker.

Also consider an “Auto” detail mode:
- compact normally;
- temporarily expand during Governor decisions/problems.

---

# 10. Advanced is currently a warehouse

Current Advanced contains:
- Launch Option;
- All Settings;
- Journal;
- System;
- Inspector with Saved / Effective / Governor / Actual.

Everything difficult was moved there, but nothing was truly removed.

That is not simplification. It is storage.

## Recommendation

Split into two concepts:

### Settings
Normal user-facing preferences:
- Mode default;
- Overlay;
- per-game preference;
- notifications;
- startup behavior.

### Diagnostics
Technical/support:
- Pipeline state;
- logs;
- engine info;
- runtime;
- journal;
- raw config;
- Flatpak state.

Diagnostics should be visually marked as technical.

---

# 11. “All Settings” should never be normal product UI

The generic schema-driven editor is useful for:
- development;
- emergency recovery;
- testing new fields.

It is bad normal UX.

A polished product should not expose its config schema as a settings screen.

## Recommendation

Rename:
`Developer settings`

Hide behind:
`Settings -> Diagnostics -> Developer`

Potentially require an “Expert mode” toggle.

Do not delete the editor from code yet because it is useful during development.

Delete it from the normal user journey.

---

# 12. Journal is a backend safety feature, not a navigation feature

Configuration Journal is excellent architecture.

But users do not need a permanent “Journal” button.

Normal recovery UX should be:

> Last change caused a problem.
> Restore previous settings?

The actual journal belongs in Diagnostics.

---

# 13. System page exposes too much deployment machinery

Current System page exposes:
- installed state;
- version;
- expected version;
- install;
- reinstall;
- uninstall;
- Flatpak runtimes 23.08 / 24.08 / 25.08;
- app-by-app Flatpak overrides.

This is classic inherited project plumbing.

## Recommendation

Normal Settings -> System should show only:

### Engine
`GFG Engine · Ready`

If update needed:
`Update available`
[Update]

If broken:
`Repair engine`

No “Reinstall” unless repair failed.
No “Uninstall” in the primary flow.

### Compatibility
Automatically detect required Flatpak runtime.

Do not ask the user to understand runtime 23.08 vs 24.08 vs 25.08.

Show per-app integration only if GFG cannot configure it automatically.

Raw runtimes belong in Diagnostics.

---

# 14. Pipeline Inspector is excellent diagnostics and terrible normal UX

Saved / Effective / Governor / Actual is valuable when debugging.

It is not a normal settings concept.

Keep it.

Move it to:
`Diagnostics -> Pipeline`

Potentially make it even better there, because once hidden from normal users it can be unapologetically technical.

---

Keep this short.

- maybe minimum experience preference later.

### Overlay

- detail;
- position.

### Per-game
- current game's preferred mode;

Technical entry at the bottom.

# 18. DIAGNOSTICS

Put the old project's useful machinery here:

- Record log;
- Pipeline Inspector;
- Configuration Journal;
- Developer settings;
- Engine details;
- Flatpak runtimes;
- app overrides;
- raw telemetry;
- launch command;
- session traces.

This preserves every useful engineering capability without making it part of the product's identity.

---

# 19. Contextual UI instead of permanent buttons

This is the biggest UI philosophy change.

Do not show a button because the feature exists.

Show it because the user currently needs it.

Examples:

### Engine missing
Show:
`Install GFG Engine`

After installation:
hide it.

### Game missing launch command
Show:
`Enable GFG for this game`

After correction:
hide it.

### Telemetry broken
Show:
`Record diagnostics`

Healthy state:
hide it.

### Flatpak integration missing
Show:
`Enable integration`

Configured:
hide it.

### External TDP controller detected
Show explanation and action only then.

This can eliminate half the visible controls without deleting any capability.

---

# 20. What should be removed from normal UI immediately

## Remove from Home
- Frame Generation
- Scaling
- HUD
- Profile
- Advanced list row in its current form
- Launch Option section
- Log Recorder section

Replace with:
- Mode
- Details
- Settings icon

## Remove from normal Settings
- Saved multiplier
- Scale-ready launch
- All Settings
- Journal
- raw Pipeline Inspector
- manual Flatpak runtime versions
- reinstall/uninstall as primary actions

Do not necessarily delete backend support.

Just stop asking normal users to operate the engine room.

---

# 21. What should stay visually almost unchanged

The current design system is one of the stronger parts.

Keep:
- red/black palette;
- one accent color;
- rounded cards;
- spacing;
- ring;
- hero composition;
- status hierarchy;
- primary RUN button;
- compact Real -> GFG -> Output visualization;
- restrained motion;
- current Steam Deck-friendly focus treatment.

Avoid redesigning the whole visual identity again.

The next UI work should mostly be deletion and hierarchy, not cosmetics.

---

# 22. New telemetry should not create new clutter

Frametime, temperature, GPU, CPU and confidence are useful.

Do not turn Home into MangoHud.

Home should show only the few metrics that answer:
- smooth?
- hot?
- efficient?

Recommended Home metrics:
- output FPS;
- real FPS;
- multiplier;
- frametime;
- TDP;
- temperature.

Everything else:
Details.

GPU %, clocks, CPU saturation, actual package power, p95/p99:
Details/Diagnostics.

---

# 23. Avoid “expert mode” becoming another junk drawer

An Expert/Developer area is useful, but it should not become an excuse to keep every old feature forever.

For each legacy control ask:

1. Does Governor need this automatically?
2. Does the user need this manually?
3. Is it only useful to diagnose a failure?
4. Is it only useful during development?

Then:
- automate;
- expose;
- move to Diagnostics;
- or delete.

---

# 24. Suggested implementation order

## UI cleanup v1
1. Remove LaunchCopy and LogRecorder from Home.
2. Replace six Home rows with Details + Settings.
3. Move mode selector to Home.
4. Move HUD to Settings.
5. Hide Scaling page from normal nav.
6. Hide FG backend/saved multiplier in Advanced/Compatibility.
7. Move Profile CRUD to Advanced.
8. Move Inspector/Journal/All Settings to Diagnostics.

## UI cleanup v2
1. Contextual onboarding cards.
2. Contextual error actions.
3. New Details page.
4. Telemetry cards.
5. confidence/reason text.
6. battery savings presentation.

## UI cleanup v3
1. per-game learned model UX;
2. reset learning;
3. compare current vs baseline;
4. efficiency/savings history if useful.

---

# Final judgment

The current UI does **not** need another visual redesign.

It needs subtraction.

The hero already communicates the right product:
- automatic;
- powerful;
- clean;
- focused.

The legacy pages communicate the opposite:
- configure everything yourself;
- understand every subsystem;
- manage runtimes;
- manage profiles;
- manage engine internals.

GFG Extreme should trust its Governor enough to hide its own machinery.

The strongest possible UI direction is:

> one screen for control,
> one screen for explanation,
> one screen for settings,
> one hidden diagnostics area.

Everything else is implementation detail.
