# GFG Shell: аудит неудач shell-fix-2 → shell-fix-5

Аудит от 13 октября 2026. Проверенный HEAD ветки `feature/gfg-steamos-shell-20261013`: `980da65ea3cc0643df9022a70a0380bc4841c57a`. PR #128. Стабильная 2.1.1 не менялась. Это исследование причин, не подтверждение готовности новой оболочки.

## Источники и уровень доказательств

Изучены исходники на указанном HEAD: `py_modules/gfg_plugin/steam_shell.py`, `themes/gfg-shell/runtime.js`, `themes/gfg-shell/shell.css`, `frontend/harness/steam-shell.mjs`, `frontend/src/app.js`, `docs/GFG_STEAMOS_SHELL.md`; история PR и изменения указанных ниже коммитов. Исходники последних шести файлов сохранены локально отдельно от старого рабочего checkout.

Наблюдения с устройства взяты из предоставленного заказчиком ТЗ и разделов Connection correction документа `GFG_STEAMOS_SHELL.md`. В этом сеансе не получены исходный CDP dump устройства, реальные снимки восьми экранов или видео. Числа узлов не выданы за самостоятельно снятую телеметрию. Два новых PNG заказчика являются эталонами дизайна, а не доказательствами работы приложения.

## 1. Неверная модель окон Steam

Исходный фильтр принимал HTTPS `steamloopback.host` и небольшой набор заголовков. В `acd42bfc8b7ee2ddfa3431f8baa3d3649e8080a8` (shell-fix-2) появились SharedJSContext и browser CDP. Однако видимые окна Deck могли иметь `about:blank?createflags=…` и `about:blank?browserviewpopup=…`; они всё ещё исключались.

Исправление `a4359c5e0425c3d7601855a41ba5f0be4be7fb95` (shell-fix-3) ввело `target_kind`, проверку пары title/URL и роли main/overlay/shared. Задействованы `steam_shell.py`, `runtime.js`, browser harness и backend tests.

Доказательство из документации/ТЗ: Big Picture и QuickAccess/MainMenu — отдельные внутренние CEF targets; наличие SharedJSContext не означает доступ к видимому окну. Ранее пользователь видел Waiting for Steam Gaming Mode.

Недостаток тестов: FakeSteam возвращал только заранее допущенный HTTPS target. Даже реальные HTTP/WebSocket тесты shell-fix-2 использовали сконструированный список targetInfo. Они проверяли протокол, но не полноту модели реальных окон.

Предотвращение: сохранять инвентарь реального CEF с версией клиента, ролью, исходным URL и идентификатором окна. Отдельно проверять обнаружение, открытие сессии и наличие видимого документа. Сохранять регрессии для нативных URL; не расширять разрешение на произвольные about:blank или внешние origins.

## 2. Селекторы стали ошибочным условием существования интерфейса

После обнаружения окон `runtime.js` требовал совпадения строк вроде `gamepadhome_` и `gamepadlibrary_`. Это детали конкретной сборки Steam, а не контракт наличия UI. Документ может быть полноценным и иметь полностью другие классы.

Доказательство из ТЗ/документации: документы примерно с 1153, 597, 74 и 5 узлами возвращали `waiting-for-supported-surface`. Число узлов само по себе не доказывает, что это определённый экран или что его функции известны.

`6263ae371220a2d4ab283773e5d76725ba1e28d7` (shell-fix-4) добавил fallback для проверенной роли и DOM ≥40 узлов. Он позволял внедрить стили без совпадения классов; это исправление условия внедрения, не реализация screen adapter. Файлы: `runtime.js`, `shell.css`, `steam_shell.py`, `frontend/harness/steam-shell.mjs`, `frontend/src/app.js`.

Недостаток тестов: исходный harness сам создавал имена классов, которые искал код. Поздняя фикстура с 1153 div воспроизвела отсутствие классов, но не настоящий DOM Steam. Проверка переменной цвета и числа кнопок не проверяет действия Steam, маршруты или компоновку.

Предотвращение: собственные screen components и явный адаптер данных/действий. Рендерер не должен распознавать свои экраны по внутренним классам Steam. Способ получения реальных данных выбирается после проверки на устройстве; отсутствующая capability означает недоступное действие, а не успешную имитацию.

## 3. URL CDP target ошибочно приравнен к URL исполняемого документа

В shell-fix-4 fallback зависел от `isNativeWindow`, вычисленного по текущему `location`. CDP описывал внутреннее нативное окно, но код исполнялся уже в документе `steamloopback.host`. Роль была корректной, условие fallback — ложным.

Доказательство из раздела shell-fix-5 документации: main, два overlay и shared были обнаружены, но документы с 1153/598/74/5 узлами отклонялись. Разница 597/598 сохранена как наблюдения разных снимков, а не исправлена задним числом.

`64549b4bb9106c4178f2051791318038ac060fd6` допускает оба проверенных вида документа при роли main/overlay. `65b0f728dce65c42ef07497223e204d85764bc71` добавляет регрессию loopback + роль main; `3ffa5c81c2ab30c63b603be76b691693d425f349` показывает documentKind и shell-fix-5. Документирование завершено `980da65ea3cc0643df9022a70a0380bc4841c57a`.

Недостаток тестов: target metadata и executing document всегда представляли один URL. Проверки не охватывали смену контекста, окна и навигацию между проверкой target и выполнением скрипта.

Предотвращение: отдельно хранить target identity и document epoch; перепроверять origin после навигации; отклонять устаревшие операции; тестировать комбинации native target/loopback document и обратный переход. Не превращать это в разрешение для внешнего сайта.

## 4. Успешное внедрение CSS подменило создание оболочки

Это основная архитектурная ошибка. В shell-fix-5 `applyGfgShell` создаёт STYLE, меняет атрибуты корня, запускает lease и возвращает `applied: true`. Он не создаёт Home/Library/Game/Downloads или другие компоненты, не загружает библиотеку и не связывает собственные элементы с реальными действиями Steam. `shell.css` сохраняет нативную структуру и перекрашивает её. Документация прямо описывает сохранение native layout.

`SteamShell.status` превращает любой `applied` в `active`, а `ThemePage` показывает GFG appearance active. Это свидетельствует только о внедрении стиля. Ни собственный renderer, ни визуальное совпадение не проверяются.

Доказательство из предоставленного ТЗ: main/overlay показали `native-loopback-target`, shared остался на `waiting-for-supported-surface`; пользователь увидел изменённые переключатели без новой структуры. Маленький служебный shared-документ может правомерно не содержать видимого экрана.

Недостаток тестов: сохранение числа кнопок, `--gfg-shell-red`, цвет canvas и один onclick доказывают обратимость CSS в синтетическом документе. Они не доказывают запуск игры, библиотеку, downloads, controller focus, реальные системные изменения или соответствие эталону. Ни один тест не измерял IoU, границы, Delta E00 или визуальные состояния восьми экранов на устройстве.

Предотвращение: перестать наращивать этот CSS как продукт. Сохранить transport и recovery-подход, заменить продуктовый слой собственной компоновкой. Разделить `transport.connected`, `injection.acknowledged`, `renderer.visible` и `device_validation.passed`. Последнее устанавливается только внешним протоколом приёмки, связанным с коммитом и устройством, никогда ответом Runtime.evaluate.

## Решение по дальнейшей работе

Транспорт shell-fix-5 — исходная контрольная база, не готовая оболочка. Новые рабочие экраны должны появляться только после проверки Steam Adapter на реальном клиенте. Повторение схемы «придумать HTML → подтвердить на нём CSS → отдать ZIP» запрещено.

Ни одна из четырёх ошибок не считается предотвращённой только наличием ещё одной синтетической фикстуры. Требуются сохранённые контрактные наблюдения устройства, функциональный прогон и отдельная визуальная приёмка. Текущая блокировка среды зафиксирована в `GFG_SHELL_ENVIRONMENT_BLOCKER.md`; стабильная публикация и merge не допускаются.
