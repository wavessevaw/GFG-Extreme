## Source observations

Evidence class in this section is **source**, unless stated otherwise. Code presence is not proof of correct runtime behavior.

* `plugin.py` implements Decky startup, one-second loop, unload/uninstall and RPC methods. `service.py` links fresh engine status, rates, settings, Autopilot, pilot, coordinator, Governor, controllers, HUD and telemetry. `Service.stop` stops and restores owned controllers.
* `policy.py` sends engine policy with a revision and waits for a fresh status echo and matching values. It has offline, outdated, stale hold, applying, confirmed, conflict and error states. Its epoch changes when relevant policy inputs change. `service.py` includes policy and controller changes in the Governor's measurement epoch.
* `service.py`, `split_control.py`, and `gpu_clock_control.py` implement interlocks: GPU clock checks whether Split owns or is settling; Split requires a settled Governor and unowned GPU clock; the Governor is informed of active probes. `lease.py` is explicitly **shadow** observation, not an enforcing lock. These interlocks and restore paths require further fault and hardware testing.
* `settings.py`: schema 3; default profile `auto`, base FPS 45 (normalized 20–90), objective Autopilot; objectives Autopilot/Battery/Balanced/Quality; global HUD on, top-right, standard; power, split and GPU clock enabled; HDR generation and HDR output enabled; above x3 and Boost disabled; Boost defaults to 1.5, choices 1.25/1.5/1.75; telemetry standard. Profiles may be default or per Steam app. HUD positions are four corners and details minimal/standard. Autopilot preferences are auto/battery/smoothness.
* Although `FG_MODES` lists fixed and custom values, `normalize_profile` retains only `off` or `auto`. `frontend/src/app.js` toggles Off on a second tap of the selected mode and selects Auto when a mode is tapped. Therefore a claim that 3.2.2 exposes fixed multiplier selection cannot be inferred from the constant or from an older protocol. Engine capabilities and UI accessibility must be audited separately.
* **Known divergence in current main** `94739b1f462ff1bd4411d8c8514bcde4d2dcb222`: `frontend/src/app.js` mode cards send only an objective and highlight it even when FG is off; a separate FG card was reintroduced. The 3.2.2 second-tap Off / mode-tap Auto behavior required by the specification is absent in that source. The owner confirmed that the card's return was a mistake. This is a source finding; no new frontend runtime test has been run. Restoration needs a regression test; the specification also requires access to fixed multipliers, which must be reconciled without silently discarding functionality.
* `filters.py` defines 19 effects, eight presets, CAS/DLS sharpening, FXAA/SMAA, sharpness and denoise normalized to 0–1. Its source describes post-processing after generation and before HUD. HDR behavior needs engine and device verification.
* `kedavra/install.py` documents bind mounting and a boot watchdog; `migration.py`, `legacy_cleanup.py`, and `kedavra/system_profile.py` implement migration, cleanup and runtime system profile paths. The latter touches runtime kernel settings; the full set and restoration semantics still require audit.
* Installer source copies the bundle to `/var/lib/kedavra/runtime.new`, checks libraries and `--version`, deletes the previous runtime and renames the new one **before** `setcap`. A failing `setcap` therefore reports failure after the previous runtime was removed. An injected failure with the existing `FakeSystem` and a temporary root reproduced this for both 3.2.2 and main `94739b1`: the installed binary was the new one, not the old one. This is a software reproduction, not evidence of an observed Deck outage. `tests/test_kedavra_install.py` checks a successful install and simulated unhealthy boot; a permanent test should assert preservation on upgrade failure. On an unhealthy boot `BOOT_SH` disables the mount, but the unit subsequently runs the profile script, which checks `profile_off`, not `disabled`. The [isolated Linux test](https://github.com/wavessevaw/GFG-Extreme/pull/180) ran both scripts with a temporary fake setting and reproduced its modification after rollback; actual kernel settings and Deck recovery remain UNVERIFIED.
* The 3.2.2 system profile is installed and executed by the engine installer, also on boot. It writes runtime `/proc/sys` and `/sys` settings (including memory, I/O scheduling, kernel watchdog settings), and a memlock limits file. Its original restorer deletes its saved journal after attempted writes even if a write fails; 3.3.3 commit `0836f16` adds preservation and error handling for failed restores. These are historical source findings; don't infer device recovery from the unit tests. Do not introduce additional kernel or security changes without owner authorization.
* Startup invokes 2.x migration only when no current settings exist; it backs up legacy data, maps profiles with Steam app IDs, reports skipped process-name-only profiles, and does not reuse old performance measurements. Decky unload cancels tasks then calls `Service.stop` and telemetry flush. Commit `0836f16` later changes worker draining and restoration; examine its regression tests before modifying lifecycle behavior.
* Baseline source sets battery/charger cache to 2 s (`service.py`), sensor discovery to 60 s (`host_sensors.py`), telemetry flush to 30 s (`telemetry.py`), and caches a successful mount check (`plugin.py`). Six power reads per second is a release claim requiring independent measurement; a negative mount result is not cached by that expression.

## Engine source map

At GSF `62621c4`, `kedavra/engine/kfg_plan.h` defines luma pyramid reduction, bidirectional motion estimation, scene-cut statistics and separate selection/repair/warp reconstruction passes. `kedavra/sched/kfg_sched.h` selects real, generated or repeated frames on the vblank grid, tracks late source/analysis, degradation and recovery; Silk uses fractional catch-up. `kedavra/gamescope/src/kfg/kfg.cpp` integrates scheduling, history, GPU submissions, status, tracing, filters and HUD into Gamescope. Source comments describe splitting analysis across two vblanks; this is not a measured GPU cost or latency.

The engine distinguishes SDR, PQ and scRGB, uses float internal colour for HDR, and restricts HDR post-processing: PQ omits colour grading and scRGB post-processing is bypassed (`PostFor`). These are code observations, not a visual quality result. The standalone `kedavra/Makefile` defines scheduler, Auto, completion-bridge, pacing and Vulkan correctness tests; `make test` needs a C toolchain, shader compiler and Vulkan ICD. The baseline release workflow builds the bench and Gamescope, but building a test executable is not evidence that the engine correctness suite ran. Separate engine tests, actual SDR/HDR quality, presentation, VRR, power and end-to-end latency remain UNVERIFIED.

## Existing checks and gaps

The baseline includes Python unit tests, 39 named virtual Deck scenarios in `sandbox.run`, seeded stress in `sandbox.stress`, and a frontend smoke harness. CI runs unit tests, sandbox, frontend build freshness and smoke; the release workflow additionally builds the engine and Gamescope. Stress is not in either baseline workflow. The baseline unit test asserts only at least 20 scenarios. This is a historical CI result, not a new execution or device evidence. The local Windows Python 3.12 run reports 169 tests, two failures and seven errors; Unix shell, `os.chown`, and Linux sysfs assumptions account for several errors, but each failure must be classified before drawing conclusions. The UTF-8 sandbox repeat passed 39 scenarios and saved detailed JSON. Stress with seeds 1–30 passed all 39 runs. Both are simulations. Detailed local logs are retained separately with the audit workspace.

The baseline release workflow responds to `v3.*` tag pushes and manual dispatch. The latter can create a tag and publish; existing releases receive assets with `--clobber`. Its test job does not run stress. The current default-branch workflow still contains the tag/manual triggers and clobber behavior. On 2026-10-30 GitHub's branch response reports main `protected: false`, and the repository rulesets listing is empty; detailed branch protection API returned 403 to the integration. A workflow alone cannot enforce owner approval or block direct pushes. Repository protection and release controls still require action.

## Diverged history and saved-setting regression

The baseline `92b557f678d118ae97948673c26e2498b7a28467` and main `94739b1f462ff1bd4411d8c8514bcde4d2dcb222` diverged from merge base `0124c02a88d3ead3fc27f5c3a6af41cdcb5e1c0c`; the baseline is not an ancestor of that main. Source comparison and branch history matter when assessing lost behavior.

The four missing historical sandbox checks are not simple renames:

* `battery_drains_autopilot`: the baseline expected a low-battery Autopilot point of 24 with above-x3 allowed, and 30 with the default lock. Main changed this in `565486c` to keep a 55 FPS game in the 35–45 family; the stated reason was a reported drop from 45 to 30 at low battery. The resulting FPS, pacing, energy and quality trade-off has not been measured on hardware. Neither a mathematical equivalence nor a waiver of the baseline requirement is established.
* `fixed_x3_too_heavy`: baseline branch commit `932eaed` converted fixed x3 settings to Auto and tested that Off stayed Off. Main kept fixed choices instead. The owner explicitly requires fixed modes to remain available, so coercion to Auto conflicts with that requirement; it must not silently be relabelled as an equivalent passing check. The [separate reproducibility PR](https://github.com/wavessevaw/GFG-Extreme/pull/183) tests preservation of fixed settings and Off in memory, but not the frontend or real engine.

Main commit `861f749` introduced schema 4 defaults and unconditionally sets Power Split and GPU Clock false when normalizing schema 3 data, even when their saved values are true. On 3.2.2, all four true/false combinations survive normalization. On main, a local in-memory reproduction fails for the three combinations containing true; a mocked later save would persist the changed values. PR #183 contains the failing checks; its Linux CI reproduced the three failing combinations and the subsequent-save failure among 200 tests. The original code comment cites pacing costs as a reason for new defaults, but that is not evidence of permission to overwrite saved choices or proof that re-enabling controllers is safe without coordination and hardware tests. Product behavior and hardware recovery are not fixed or verified by this finding.

`lcd_unlocked_75hz` retained its check names, but commit `0427f2e` changed the model input from 40 to 41 FPS at 15 W; its message says this supplied a margin above the noise line. With the original 40 input, an independent [regression test](https://github.com/wavessevaw/GFG-Extreme/pull/184) passes on 3.2.2 and `0427f2e`'s parent `7244d9a`, but finishes at point 35 instead of 37 on `0427f2e` and main. Linux CI reproduces the failure. This locates a change between revisions, but does not establish its precise cause or real LCD behavior. The 41 input is retained as an additional case; it does not replace the original condition.
